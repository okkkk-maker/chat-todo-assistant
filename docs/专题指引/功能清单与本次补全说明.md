# 待办自动汇总助手 · 功能清单与本次补全说明

版本：v1.3.0（R8）
日期：2026-11-05
范围：`1-实施员一键初始化包`（实现/初始化侧）与 `2-用户日常全自动运行包`（日常运行侧），两份代码同构。

## 一、整体架构与数据流

```
                         ┌──────────────────────────────┐
                         │  定时采集（新增 scheduler）    │
                         │  interval / daily 两种计划     │
                         └──────────────┬───────────────┘
                                        │ 按计划执行
                                        ▼
  ┌───────────┐   ┌──────────────┐   ┌────────────────────┐
  │ QQ 本地库  │   │ 微信本地库    │   │ 飞书 OpenAPI        │
  │ nt_msg.db │   │ SQLCipher4   │   │ 企微/钉钉(收件箱)    │
  └─────┬─────┘   └──────┬───────┘   └─────────┬──────────┘
        │ extract_impl   │ wxkey+wxdecrypt      │ channels/feishu、inbox
        └────────────────┴───────────┬──────────┘
                                     ▼
                        channel_collector.run()   统一契约 ChannelResult
                                     ▼
                        work/待办素材.json  {meta, messages[]}
                                     ▼
              ┌──────────────────────────────────────────┐
              │ WorkBuddy 定时任务（automation-prompt）    │
              │ 判状态 → 提炼待办 → 溯源 → 写清单 → 推送   │
              └──────────────────────────────────────────┘
                                     ▼
                     output/todo-*.md ＋ 企微（连接器/Webhook）
```

关键设计约束（一直有效，本次未改）：
1. **不臆造**：每条素材必须有 `source/chat_id/sender/timestamp/msg_id`。
2. **不静默**：任何通道没读到都要落 `output/异常说明-*.txt` 并在清单首行报警。
3. **不用 0 条冒充正常**：`message_count=0` 且 `data_state` 不是 `no_new/only_noise` 时禁止说「没有待办」。
4. **游标只前进到已处理水位**，任一通道失败即冻结，避免整段时间丢失。

## 三、缺失与缺漏清单（补全前的真实状态）

### 3.1 定时任务调度（完全缺失）

| 现象 | 证据 | 影响 |
|---|---|---|
| 控制台「调度线程守护中」「⏸️ 调度器已挂起」是装饰 | `server.py` 中 `IS_SCHEDULER_RUNNING` 只是布尔量，`/api/control` 翻转它仅写一条日志，无任何线程读取 | 用户以为在自动跑，实际从不自动采集 |
| 没有计划文件 | 全项目无 `schedule.json`，无 `interval/cron` 概念 | 无法表达「每 30 分钟」或「每天 8:30」 |
| 「定时任务」全靠人手动建 | `说明-实施员.txt`、`admin_init.py` 结尾都写着「在 WorkBuddy 里新建定时任务」 | 实施环节漏一步，整套系统就不自动 |
| 开机自启只跑一次 | `setup_autostart.py` 写的是 `run.py --no-open`，登录后跑一次就退出 | 之后再也不采集 |
| 用户包永远不生效 | 自启 BAT 写死 `.venv\Scripts\python.exe`，不存在就 `exit /b 1`；2-包没有 `.venv` | 自启静默失败 |
| 提示词与调度脱节 | `automation-prompt.md` 每轮都要求 `run.py --hours 24` | 与自动采集重复执行、互相抢锁 |

### 3.2 微信密钥与消息读取（链路断在多处）

| # | 问题 | 证据 | 后果 |
|---|---|---|---|
| 1 | **解密调用少传一层目录** | `channels/wechat._try_decrypt()` 传 `WECHAT_DATA_ROOT=source.parent`（即 `<wxid>_xxx`），而 `decrypt_all.py` 按 `<root>/*/db_storage` 匹配；`extract_raw_key.auto_decrypt()` 同样错一层 | 「密钥抓到了，但一个库都没解出来」——最典型的假失败 |
| 2 | **密钥写入不校验** | `health.handle_wechat_key_sync()` 从 `key_windows.txt` 正则取 64 hex 直接写 `.env` | 旧账号/旧机器的过期密钥静默生效，之后只报「解密失败」 |
| 3 | **校验条件过严** | `extract_raw_key.verify_candidate()` / `decrypt_all.py` 都要求 `pt[4]==0x50`（reserve 必须 80） | reserve 不同的库会把**正确密钥**判成错密钥 |
| 4 | 校验条件过宽 | 上面同一函数只看 3 个字节，不看页大小/格式版本 | 误判概率升高，PBKDF2 白跑 |
| 5 | **R7 用内存扫描替换了已验证可行的 Frida 方案**，但策略不完整 | `docs/2026-06-06-windows-raw-key-journey.md` 明确结论：「内存里没有裸 K1/raw key，必须 hook HMAC ipad」；R7 只保留「salt 邻域 + x'' 模式」，且 `max_verifications=40/15` 提前收手 | 多数机器扫不到，且失败信息只有一句「未即时捕获」 |
| 6 | `hdr_ok` 判据写死 reserve=80 且只查 3 字节 | 同 #3 | 正确密钥被拒 |
| 7 | 进程过滤只按名字，缺权限诊断 | `get_wechat_pids()` 只筛 `weixin.exe/wechat.exe`，`OpenProcess` 失败时返回 None 无原因 | 「什么都没发生」，无法排障 |
| 8 | 消息正文压缩未处理 | WeChat 4.x 部分 `message_content` 为 zstd（`28 B5 2F FD`）；工程内无 zstd 依赖 | 这类消息静默变空 |
| 9 | 群聊发送人还原粗糙 | 直接显示 `real_sender_id` 或「未知发送人」，未用正文 `wxid:\n` 前缀，也未读通讯录 | 溯源价值低（「谁说的」不清楚） |
| 10 | 表结构差异被静默吞掉 | `skipped_tables` 只累加，不进 `note`（旧版） | 微信升级后「条数莫名变少」 |
| 11 | 「模拟测试」是假跑 | `mock_wechat_test.py` 把明文 sqlite 拷进镜像目录 + 写 4096 字节全零假库，并**覆盖真实 `.env` 与 `active_platforms.json`** | 打印「100% 跑通」，实际没验证解密；还会污染用户配置 |
| 12 | 镜像落 vendor 目录 | `decrypt_all.py` 写到 `vendor/wechat-key/decrypted`，2-包没有 vendor | 用户包根本无法用 |
| 13 | 通道文案与实际能力不符 | `server.py` 用 `has_vendor` 判断微信是否就绪 | 灯是绿的但采不到 |

> 真机实测（Windows 10 + 微信 4.0.6.55，账号标识已脱敏 `<wxid>`）：
> 确认数据目录与 `message_0.db`（2.8MB，salt `77cb37d9…`，4096 页、reserve 80）真实存在；
> 对内存做 **salt 邻域 ±256 字节 × 6 处命中**、**全量 889MB 扫描 2880 个 32 字节窗口**做 AES/PBKDF2 验证，
> 结果 **K1=0、raw=0** —— 与 vendor 文档「静止态内存里没有裸密钥」的结论一致。
> 这说明：**只靠 salt 邻域盲扫是注定失败的**，必须依赖结构化缓存 `x'<key><salt>'` 或 hook。

## 四、补全功能一：定时任务调度能力

### 4.1 设计

分两层，各管一段，互不阻塞：

| 层 | 职责 | 落点 |
|---|---|---|
| 程序侧调度器 | 按计划**采集**（`run.py --no-open`），落 `work/待办素材.json` | `tools/scheduler.py` |
| WorkBuddy 定时任务 | **提炼 + 写清单 + 推送**（读素材，不再重复爬数据） | `automation-prompt.md` → 已建成自动化 |

调度器刻意不依赖 `schtasks`：目标机常无管理员权限，且非交互会话拉起的进程历史上出现过"空壳"。改用「常驻线程 + 启动文件夹」，与项目既有自启机制一致。

### 4.2 文件与接口

**新增 `tools/scheduler.py`**

- 计划文件 `config/schedule.json`：

```json
{ "enabled": true, "mode": "interval", "interval_minutes": 60,
  "daily_times": ["08:30","12:30","17:30"], "hours": 6,
  "max_runtime_seconds": 900, "skip_if_last_unfinished": true, "quiet_window": [] }
```

- 状态文件 `work/schedule_state.json`：`last_start/last_end/last_rc/last_output/next_run_text/history[-30]`
- 日志 `output/scheduler.log`，PID `work/scheduler.pid`
- CLI：
  ```
  python tools\scheduler.py status
  python tools\scheduler.py run-now [--hours N]
  python tools\scheduler.py daemon
  python tools\scheduler.py --interval 30        # 改成每 30 分钟
  python tools\scheduler.py --daily 08:30,17:30  # 改成每日两次
  python tools\scheduler.py enable|disable|config
  ```
- 并发：真正互斥仍由 `run.py` 的文件锁保证；调度器只额外做「上一轮未结束就跳过」，避免堆积。

**改 `server.py`**

| 位置 | 改动 |
|---|---|
| 顶部 | `import scheduler as sched`；`SCHEDULER_THREAD` 全局 |
| `main()` | 新增 `--no-scheduler`；默认按配置拉起 `sched.daemon_loop` 线程 |
| `GET /api/schedule` | 返回调度状态（next_run、last_rc、history…） |
| `POST /api/schedule` | 保存 `mode/interval_minutes/daily_times/hours/enabled`（带校验） |
| `POST /api/control` | 由「翻转布尔量」改为**真启停**：写配置 + 起/停线程 |
| `GET /api/status` | 新增 `schedule` 摘要字段 |
| `GET /api/wechat/key-status` | 微信通道体检（新增） |

**改 `tools/setup_autostart.py`**

- 新增 `ChatTodoScheduler.bat`（`scheduler.py daemon`），登录后常驻；
- 解释器改为 `_python_exe()`：有 `.venv` 用 `.venv`，没有则用当前解释器 —— 修掉用户包自启静默失败。

**改 `tools/admin_init.py`**：初始化收尾改为注册常驻调度 + 生成默认 `schedule.json`，汇总表里「开机自启」改为「采集调度」。

**改 `automation-prompt.md`（并在 `.local.md` 同步渲染）**

- 开头增加「分工说明」：采集归调度器，提炼归你；
- 新增 **0.5 节**：先 `scheduler.py status` 判断调度是否在跑，三种结果三种处置；
- 第 2 步改为「先看素材新鲜度（90 分钟内就跳过），否则 `run.py --hours 24 --no-open`」；
- 遇到「另一个实例正在运行」→ 等 60 秒重试一次，不反复点；
- 排障速查表按新增的微信错误分类重写。

## 五、补全功能二：微信本地密钥 + 消息读取

### 5.1 密钥从哪来（四种来源，统一校验闸门）

| 顺序 | 来源 | 说明 |
|---|---|---|
| 1 | `.env` 的 `WX_DBKEY` | 已有密钥，先校验再用 |
| 2 | 密钥文件 | `vendor/wechat-key/key_windows.txt`、`work/wx_key.txt` |
| 3 | **内存扫描**（主力） | 微信进程 `x'<32B key hex><16B salt hex>'` 结构化缓存 |
| 4 | 人工粘贴 | 控制台/CLI 传入 |

**任何来源都必须通过 `wxdecrypt.key_matches_db()` 才能被采用**：解密 page 1（IV 取页尾 reserve 区首 16 字节），校验页大小 0x1000、写/读格式版本 ∈ {1,2}、负载比例 64/32/32。通过才写 `.env` 与 `key_windows.txt`。

### 5.2 数据来源（全部本机、只读）

| 数据 | 路径 | 用途 |
|---|---|---|
| 消息主库 | `xwechat_files/<wxid>/db_storage/message/message_0.db` | 会话正文（`Msg_<md5(wxid)>` 表）、`Name2Id` 映射 |
| 消息分片 | `message/message_N.db` | 同一账号的多分片 |
| WAL | `message_0.db-wal` | 未落盘的已提交事务（先按 SQLite 语义合并再解密） |
| 通讯录 | `db_storage/contact/contact.db` | wxid → 备注/昵称（best effort） |
| 账号标识 | 目录名 `wxid_xxx_demo` | 判定「本人发言」与镜像归属 |

### 5.3 消息类型覆盖

| `local_type` | 类型 | 是否产出待办素材 | 提取内容 |
|---|---|---|---|
| 1 | 文本 | ✅ | 正文（剥离群聊 `wxid:\n` 前缀） |
| 3 | 图片 | ❌ 计数 | 库中无正文，仅媒体指纹 |
| 34 | 语音 | ❌ 计数 | 转写结果不在 `message_content` |
| 42 | 名片 | ✅ | 昵称 |
| 43 | 视频 | ❌ 计数 | 无正文 |
| 47 | 表情/贴纸 | ❌ 计数 | 无正文 |
| 48 | 位置 | ✅ | poiname/label |
| 49 | 链接/文件/小程序/引用/转账/红包 | ✅ | 解析 `appmsg` XML：title/des，按 `<type>` 细分 file/link/miniprogram/quote/transfer/redpacket |
| 50 | 通话 | ❌ 计数 | 只有状态位 |
| 10000 | 系统消息 | ⚠️ 视内容 | `sysmsg` → `replacemsg`（入群/群名/群公告等，多数被判为噪音） |
| 10002 | 撤回 | ❌ 噪音 | 「撤回了一条消息」不参与提炼 |
| 其它 | — | 视正文 | 走通用可读片段提取 |

压缩正文：以 `28 B5 2F FD` 开头（或 `WCDB_CT_message_content=4`）时按 zstd 解压；本机无 zstd 库时该条标记「压缩正文未能解压」，并在通道备注里汇总条数，不静默丢。

每轮通道备注固定输出「类型分布」与「解码提示」，例如
`类型分布: 文本128, 图片9, 语音3, 链接4` —— 这样"条数少"能立刻定位到是"图片多"还是"表结构不符"。

### 5.4 异常处理矩阵

| 场景 | 通道状态 | 用户看到什么 | 游标 |
|---|---|---|---|
| 没装微信 / 没登录过 | `NOT_INSTALLED` | 「没找到微信数据目录…确认已登录 4.x 或设置 WX_DATA_PATH」 | 冻结 |
| 有库但没密钥 | `NOT_CONFIGURED` | 「从未取到过密钥」+ 三种取法 | 冻结 |
| 密钥与当前库不匹配（换号/重装） | `FAIL` | 「密钥与当前数据库不匹配（salt 校验未通过）…请重新提取」 | 冻结 |
| 扫了没抓到 | `FAIL` | 「扫描 N 秒未捕获…微信在刚启动/刚打开聊天时才留密钥；重启微信后立刻再抓」 | 冻结 |
| 权限不足读不了内存 | `NOT_INSTALLED` | 「请以管理员身份运行，或确认微信以同一用户启动」 | 冻结 |
| 密钥对、解密时库正在写 | `FAIL`（库级 `BUSY`） | 「微信正在写这个库，下次采集自动重试」 | 冻结，下一轮补 |
| 单页 HMAC 不过 | `FAIL`（`CORRUPT`） | 「第 N 页校验失败（库可能正在写入）」 | 冻结 |
| 表结构不符 | `STALE` | 备注「N 张表结构不符（微信版本差异），已跳过」 | 冻结（覆盖不完整） |
| 单表 500 条封顶 / 分片数超限 / 总数超限 | `STALE` | 备注写明「覆盖不完整」 | 冻结 |
| 镜像比窗口还旧 | `STALE` | 「镜像比本次时间窗还旧，覆盖不完整」 | 冻结 |
| 全部正常但窗口内无文本 | `OK` | 「窗口内没有可提炼的文本消息」（可判 no_new） | 正常推进 |

### 5.6 与既有代码的衔接

- **仍然只经 `ChannelResult` 契约**：`channel_collector` 不需要知道微信内部换了内核；
- **密钥/镜像都在程序目录内**：`work/wx_mirror/<wxid>/db_storage`，可用 `WX_MIRROR_DIR` 迁到别的盘；
- **`extract_raw_key.py` 等 vendor 脚本仍可用**，只是不再被主链路依赖；
  `_try_decrypt()` 兼容壳内部已改走新内核，`health.py` 的旧调用点不会断；
- **游标语义未变**：微信 `STALE/FAIL` 一律冻结共享游标，下一轮从原位置补。

## 八、R9 补丁：微信取密钥超时 / 假死 / 4.1 抓不到

| 问题 | 根因 | 修复 |
|---|---|---|
| 提示“请求超时 8 秒，监控台可能已卡住” | 前端 `REQ_TIMEOUT_MS=8000`，后端同步扫描 25 秒；超时文案是写死的 | 长任务改异步 job（`/api/wechat/key-job` 轮询进度），默认超时改 15 秒，文案改为“任务可能仍在后台执行” |
| 断开后结果丢失、重复点击叠加扫描 | 同步执行在 HTTP 处理函数里 | `WX_JOB` 单飞队列；POST 立即返回 job id |
| 扫描慢（9.5 秒 / 1440MB） | 把 4 个 `--type=wxocr/...` 插件进程也扫了 | 只扫内存最大的主进程，实测降到 803MB / 约 3 秒 |
| 微信 4.1 扫不到 key | 4.1 在 PBKDF2 后清零 raw key，内存里只剩明文页缓存（实测 803MB：0 处 hex 缓存、2 处 salt、12 个候选全不通过） | 新增 `tools/wxhook.py`：启动瞬间挂载 `sha512_block`，捕获 HMAC ipad 还原 raw key，page1 校验通过才落盘 |
| hook 依赖安装失败 | frida 17.x 在 Win10 报 `Unable to locate the ntdll loader TLS routines` | 固定 16.7.19，wheel 放 `vendor/wheels`，首次使用时离线安装 |
| 旧 hook 脚本 RVA 写死 | `0x5129f80` 只适用于 4.0.0.x | 从 DLL 的 OpenSSL 版权串 + 入口特征动态解析（本机 4.1.15.56 → `0x5a18f80`） |

验证：`tools/wx_selftest.py` 全链路仍通过；控制台异步任务实测 7 秒完成、进度每秒刷新；`wxhook.py status` 可正确解析 RVA 并识别 frida 16.7.19。

已知限制：启动瞬间抓取要求**用户在桌面上手动重启微信**。从脚本/后台会话拉起的微信是空壳，不打开数据库，会在 1 分钟内退出。

## 九、R11 补丁：让微信的数据真正进得了清单

微信密钥一旦通了，剩下三处会让「素材有、清单空」，一并修掉：

| 问题 | 现象 | 修复 |
|---|---|---|
| 提示词取值写错 | 契约文档写「遍历 `meta.messages`」，而素材文件的 `messages` 在**顶层**，`meta` 里只有统计。照着写会一条都取不到，表现为「采集正常但清单为空」 | 模板与两包 `automation-prompt.local.md`、WorkBuddy 自动化提示词统一改为「顶层 `messages`」并显式注明 |
