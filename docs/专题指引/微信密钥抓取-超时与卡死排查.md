# 微信密钥抓取：超时 / “监控台卡住” / 抓不到 key 的排查与修复

> 适用版本：**v1.4.0（R10）**；R9 的“4.1 必须重启微信才能抓”已被推翻，见下方更正块。
> 实测环境：Windows 10 + 微信 4.1.15.56（`Weixin.exe` 主进程 340~840 MB，20 个加密库）

---

## 〇之前、最容易被误判的一条：控制台其实起了两份

**现象**：命令行 `python tools\wxkey.py acquire` 明明 2 秒就能取到，控制台点按钮却
永远报「扫描完成但没有找到可用的密钥」，或者界面上的设置改了不生效、状态时好时坏。

**根因**：Windows 上 `allow_reuse_address = 1` 允许**两个进程同时监听 8000**。
旧实现里 `_bind_server()` 在 8000 被占时会退到 8080 甚至随机端口，但浏览器仍然打开
8000 —— 于是请求被系统随机分给**旧进程**，跑的是旧代码。表现为「明明改了却没生效」。

**自查一条命令**：

```bat
netstat -ano | findstr ":8000"
```

出现两行 `LISTENING` 就是这个问题。**处理**：把所有监听 8000 的 PID 结束掉，只保留一个。

**已修**（v1.4.1）：

- `allow_reuse_address = False`、`allow_reuse_port = False`：第二个实例绑不上，不会再出现双监听；
- 新增 `GET /api/ping`：端口被占时先探测是不是本程序的控制台；
- 是 → 打印「控制台已经在运行」并直接退出（`--no-open` 时不开浏览器），不再悄悄换端口；
- 不是 → 才退到 8080 / 随机端口（比如 8000 被别的软件占用）。

## 〇、R10 更正（2026-11-06）：真正的根因与真正的解法

**R9 的结论“4.1 在内存里不保留密钥、只能启动瞬间 hook”是错的。**
4.1 只是把密钥换了个存放方式：

```
com.Tencent.WCDB.Config.Cipher   ← 字符串对象（标记）
        └─ node+0x28  → Config 指针
              └─ Config+0x88 → (data_ptr, data_len)  ← blob，长 99 字节常见
                    └─ blob XOR 固定 40 字节掩码
                          └─ x'<64hex key><32hex salt>'   ← 每库一把，明文可见
```

所以：

* **不需要重启微信、不需要 hook、不需要管理员以外任何权限**；
* `x'...'` 明文确实不在内存里，但**XOR 解码后就是明文**；
* 4.1+ 是**每库一密钥**（20 个库 20 把钥匙），不是一把万能钥匙；
* 校验方式改为 **page 1 的 HMAC-SHA512**：`mac_key = PBKDF2(enc_key, salt^0x3A, 2)`，
  与页尾 64 字节比对。这是**精确**判据（2^-512 误判率），比“猜页头字节”可靠得多。

R10 实测：`wxkey.py scan` **2.4 秒取到 20/20 个库**，`message_0.db` 701 页 HMAC 全通过，
7 天窗口读到 487 条消息（文本 300、链接 165、表情 40、转账 16、系统 6、引用 5、文件 3）。

| 版本 | 密钥形态 | 程序怎么取 |
|---|---|---|
| 4.0.x | 内存缓存 `x'<key><salt>'` | 老路径：扫结构化缓存（保留为兜底） |
| 4.1+ | Config.Cipher 对象内 XOR blob，每库一把 | **新路径：对象链 + XOR 解码 + HMAC 校验** |

## 一、先给结论

你看到的 **“抓取失败，请求超时 8 秒，监控台可能已经卡住”** 不是微信的问题，是控制台自己的两个缺陷叠出来的：

1. **前端只有 8 秒耐心，后端要扫 25 秒以上**
   `index.html` 里 `REQ_TIMEOUT_MS = 8000`，而 `/api/wechat/extract-key` 是**同步**执行的：扫内存默认 25 秒，成功后再解密整个 `db_storage`。请求必然先被前端 `AbortController` 掐断。

2. **“监控台可能已卡住”是写死在超时分支里的文案**
   它只说明“这个请求 8 秒没回来”，不代表服务死了。实际上后台线程还在扫，扫完的结果因为连接已断而被丢掉——所以你会看到“超时 + 最终还是没有密钥”。

3. **旧实现还会把 5 个 `Weixin.exe` 全扫一遍**
   除主进程外，还有 `--type=wxocr / wxutility / wxpublic / xplayer` 四个插件子进程。实测多读 600 MB 左右、多花 4~6 秒，而且它们根本不碰数据库。

4. **最关键的：你的微信是 4.1，静态内存里已经没有 key 了**
   实测（微信已登录、`message_0.db` 正在写）：

   | 指标 | 实测值 |
   |---|---|
   | 可读内存 | 803 MB / 提交 868 MB（覆盖率 92%，无大块被跳过） |
   | `x'<64hex key><32hex salt>'` 结构 | **0 处** |
   | salt 出现次数 | **2 次**（都在明文 schema 页缓存里） |
   | PBKDF2 候选 | 12 个，全部不通过 page1 校验 |

   也就是说：**内存里只剩明文页缓存，raw key 在派生完页密钥后就被 SQLCipher 清零了**。这不是“再点一次”“重启后 10 秒内再点”能解决的——4.1 必须换抓取时机。

## 二、按这个顺序排查（每步都有明确判据）

### 第 1 步：确认微信真的在“工作状态”

```powershell
Get-Process Weixin | Select-Object Id, MainWindowTitle, @{n='MB';e={[int]($_.WorkingSet64/1MB)}}
```

- 没有 `Weixin.exe` → 先登录微信。
- `MainWindowTitle` 是“微信/登录”而不是你的昵称 → **还没登录，数据库没打开，不可能有 key**。
- 主进程只有 100~200 MB、窗口是登录页 → 典型“空壳”，见第 4 步。
- 正常登录后主进程一般 500 MB 以上（本机 800 MB）。

### 第 2 步：确认控制台服务活着，而不是页面假死

```bash
curl -s http://127.0.0.1:8000/api/status
```

有 JSON 返回 = 服务正常；连不上才是服务退出。**不要把“请求超时”当成“服务死了”**。

### 第 3 步：直接看任务进度，而不是盯着按钮

```bash
curl -s http://127.0.0.1:8000/api/wechat/key-job
```

返回里的 `state / stage / progress.scanned_mb / progress.candidates` 就是实时进度。
如果 `state=running` 且 `scanned_mb` 在涨，说明后台在干活；如果 `scanned_mb` 不动超过 10 秒，才是真卡住。

### 第 4 步：区分“扫不到”还是“这个版本根本没有”

抓取失败时看返回的 `notes`：

- `结构化缓存 x'<key><salt>' 0 处，salt 邻域候选 ≤4 个`
  → 微信 4.1+，**静态扫描这条路已经封死**，直接跳到第三节的“启动时抓取”。
- `PBKDF2 校验 N 个候选` 但都不通过
  → 密钥可能在内存里但已被清成轮密钥，同样走启动时抓取。
- `PID xxx 打不开（错误码 5）`
  → 权限不足，用管理员身份运行。
- `没有检测到正在运行的微信`
  → 进程没起或名字不是 `Weixin.exe`。

### 第 5 步：确认微信是“桌面手动启动”的

后台/脚本/远程会话拉起的微信是**空壳**：进程在、窗口可能也有，但不读数据库、不联网，通常 1 分钟内自己退出。
判据：主进程内存长期停在 100~200 MB、日志没有登录成功记录、`db_storage` 文件 mtime 不变。

必须：**在桌面上双击微信图标 → 扫码/确认登录**。

## 三、修复方案（已落地）

### 3.1 控制台：长任务改成“异步任务 + 轮询”

旧：`POST /api/wechat/extract-key` 同步跑 25 秒 → 前端 8 秒断开 → 结果丢失。

新：

```
POST /api/wechat/extract-key {action:"scan"}   → 立刻返回 {job:"wx..."}
GET  /api/wechat/key-job                       → {state, stage, progress, result}
```

- 前端每 800 ms 轮询一次，弹窗显示“已扫描 184 MB / 校验 6 个候选”。
- 同一时刻只允许一个任务，重复点击不会叠加扫描。
- 超时文案改为“任务可能仍在后台执行”，不再误导成“监控台卡住”。
- 默认请求超时 8 s → 15 s；启动/轮询请求单独设置更长的超时。

### 3.2 扫描：只扫主进程

`health.wechat_key_scan()` 现在只把**内存最大的那个 `Weixin.exe`** 传给扫描器。
实测扫描量从 1440 MB 降到 803 MB，耗时从 9.5 s 降到约 3 s。

### 3.3 微信 4.1+：启动瞬间抓取（新增 `tools/wxhook.py`）

原理（与项目内 vendor 文档一致）：

1. 微信启动、打开数据库时会跑 `PBKDF2-HMAC-SHA512(raw_key, salt, 256000)`；
2. HMAC 初始化会构造 128 字节 ipad 块：`(key XOR 0x36)[32] || 0x36 × 96`；
3. 这个块里有 key 的明文 XOR 形式，且不受后续清零影响；
4. 在 `sha512_block_data_order` 入口挂载，只对 `num == 1` 的调用读 128 字节，命中后 XOR 回来；
5. 用当前数据库 page1 做 PBKDF2/AES 校验，**通过才写入 `.env`**。

地址不写死：从 `Weixin.dll` 里找 OpenSSL 的
`SHA512 block transform for x86_64` 字符串，再匹配函数入口特征
`48 89 7C 24 08 48 89 74 24 10 48 89 E0 48 89 CF 48 89 D6 4C 89 C2`。
本机 4.1.15.56 解析结果 `RVA = 0x5a18f80`，在进程内读到的入口字节与磁盘完全一致。

使用方式（二选一）：

- 控制台：`参数设置 → 微信 → 🚀 重启时抓取（4.1+）`
- 命令行：双击 `WeChat_Key.bat` → 选 `2`

流程：

1. 点按钮/选 2；
2. **完全退出微信（托盘图标也要退出）**；
3. 从桌面重新打开微信并登录；
4. 程序在微信打开数据库的瞬间抓取，成功后自动写 `.env` 并生成明文镜像。

> 为什么必须重启：raw key 只在“打开数据库、跑 PBKDF2”的那一瞬间存在。
> 微信已经运行一段时间后，内存里没有可用的 key，扫多少次都一样。

### 3.4 组件与兼容性

- `frida` 固定 **16.7.19**（17.x 在 Win10 报 `Unable to locate the ntdll loader TLS routines`，attach 直接失败）。
- wheel 已放入 `vendor/wheels/frida-16.7.19-cp37-abi3-win_amd64.whl`，首次使用启动抓取时**离线安装**，不联网。
- 仍然只用 `PROCESS_VM_READ` 读内存 / 只读挂载，不修改微信代码逻辑、不写微信数据库。

## 四、验证记录

| 项目 | 结果 |
|---|---|
| 803 MB 内存全量扫描 | 2.5 s，0 个读取失败块 |
| 旧逻辑扫描 5 个进程 | 1440 MB / 9.5 s（已改为只扫主进程） |
| 异步任务 | POST 立即返回，进度 1 s 内可见，7 s 完成，状态一致 |
| 4.1 静态密钥结构 | 0 处 hex 缓存；结论：必须启动时抓取 |
| `sha512_block` RVA 解析 | 0x5a18f80，与进程内入口字节一致 |
| frida attach + hook | 成功挂载，`module/hooked` 消息正常，无异常 |
| 启动瞬间端到端 | **需用户在桌面手动重启微信**（见下） |

> 端到端这一步在自动化会话里无法完成：从后台/脚本拉起的微信是空壳，会在 1 分钟内退出，不会打开数据库。
> 必须由用户在桌面上双击启动微信，这正是“启动时抓取”提示里要求的那一步。

## 五、仍然失败时，按现象对照

| 现象 | 原因 | 处理 |
|---|---|---|
| `NO_FRIDA` | 没有 frida 且 wheel 不在 | 确认 `vendor/wheels/frida-*.whl` 存在；或 `pip install frida==16.7.19` |
| `NO_DLL` | 找不到 `Weixin.dll` | 确认装的是微信 4.x；检查注册表 `HKCU\Software\Tencent\Weixin\InstallPath` |
| `NO_SYMBOL` | DLL 里找不到 SHA512 标记 | 微信大版本改了编译器/混淆；把 `Weixin.dll` 版本号反馈给维护者更新特征 |
| `NO_RESTART` | 3 分钟没检测到新进程 | 只关了窗口、托盘还在；彻底退出后重开 |
| `NO_KEY` + 进程很快退出 | 空壳（非桌面启动） | 在桌面双击启动微信，再从 `WeChat_Key.bat` 选 2 |
| `NO_KEY` + 进程稳定在 150 MB | 没登录 | 完成登录，进入主界面 |
| 候选校验不通过 | 抓到的是 page-MAC 的 mac_key | 正常现象，程序会自动丢弃并继续等；确保是在**启动瞬间**抓 |
| 密钥与库不匹配 | 换号/重装/升级 | 重新抓一次；旧密钥救不回来 |
